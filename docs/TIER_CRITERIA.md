# 티어 분류 기준 (3.x 핵심)

**한 줄 요약: 상위 모델이 정말 필요한 요청은 20%도 안 된다.** 세션 로그를 에피소드
단위로 훑어 "확실히 쉬웠던 것"만 haiku/sonnet 서브에이전트로 내리는 보수적 강등
기준이다. 전 과정 로컬 계산, LLM 호출 0회.

- 기존 라우터들의 실패는 전부 **비싼 모델로의 과잉 라우팅** 쪽 — "싼 모델로 충분한
  경우의 인식"이 미개척 지대 (RouterArena 2025)
- 난이도는 텍스트 추정이 아니라 **결과(outcome)** 로 판정 — 도구 에러·변경 수·재시도가
  로그에 이미 있다
- 저자 14일 실측(553 에피소드): **61%가 강등 후보인데 출력 토큰은 17%뿐** — 내려도
  잃을 게 적고, 남는 T0가 토큰의 83%를 쓴다

## 티어 한눈에

| 티어 | 위임 대상 | 이런 요청 | 실측 비중 | 출력토큰 | 에러 경험률 |
|---|---|---|---:|---:|---:|
| **T2** | haiku | 탐색·조회, 붙여넣은 화면 질문, 단순 실행 | 26.9% | 3.3% | 2% |
| **T1** | sonnet | 빌드 파이프라인, 상태 점검 — 변경 소수 | 34.4% | 14% | 8% |
| **T0** | 세션 모델 유지 | 에러 반복, 대량 변경, 설계·분석 | 38.7% | 83% | 36% |

에러 경험률이 2% → 8% → 36%로 갈라진다 — outcome 신호가 티어를 실제로 구분한다는
로컬 검증.

## 판정 규칙 (위에서 아래로, 첫 매치)

에피소드 = 한 사용자 요청이 유발한 연속 API 호출 묶음. 신호 6개는 전부 JSONL에서
LLM 없이 계산한다: **S1** 호출 수 · **S2** 출력 토큰 합 · **S3** 변경성 도구 수
(Edit/Write/NotebookEdit/Bash) · **S4** 도구 에러 수 · **S5** 요청 텍스트(카테고리
정규식+승급 키워드) · **S6** 위임 흔적(Task/Agent — 이미 위임된 건 제외).

```
T0 유지 (fable/opus):
  S4 ≥ 2  (에러 반복 = 어려움의 결과 증거)
  or S3 ≥ 7
  or S2 > p75(사용자 분포)        # 폴백 상수 8k
  or 승급 키워드: 설계|아키텍처|리팩토링|원인 분석|왜 |analyze|compare|evaluate|architect|refactor
  or plan-mode 진입 에피소드

T1 sonnet 후보:
  S2 ≤ p75 and S3 ≤ 6 and S4 ≤ 1 and S6 = 0
  and 카테고리 매치 (run·check·read·explore·translate 확장판)

T2 haiku 후보:
  S1 ≤ 6 and S2 ≤ max(p25, 1500) and S3 ≤ 2 and S4 = 0 and S6 = 0
  and 카테고리 매치
```

임계값(p25/p75)은 고정 상수가 아니라 **사용자 자신의 최근 14일 분포에서 스캔 시마다
재계산**한다 (표본 <100이면 폴백 1.5k/8k, T2 상한 [1k, 3k]·T1 상한 [5k, 15k] 클램프).
고정 임계값은 워크로드가 바뀌면 어긋난다는 것이 RouteLLM의 공식 한계다.

## 룰 승격과 수명 관리

- 같은 (티어×카테고리×프로젝트) 조합 **3회 이상** 반복 시에만 후보 생성 → 사람이
  promote로 승인 (오판 비용의 최종 방어선).
- 룰 텍스트에 가드 명시("단순", "읽기 전용", "결과가 명령 출력으로 판정되는") + 실패
  시 메인 모델이 이어받는 승급 경로 → 강등 오판 비용이 작다 (FrugalGPT 캐스케이드).
- **rule-health**: 승격 후 해당 유형의 에러율이 T0 평균에 접근하면(>20%) statusline
  `🅷⚠ rule-health` 경고 → 조건 축소·제거 제안. "결과로 난이도 정의"를 룰 수명에 재적용.

## 3.9 보강 — 실측 위임·상대 티어·절감액·예산 (2026-08-01)

manifest.build의 라우터 폐기 회고(HN 49126630, 7천 사용자 4개월)와 대조해 남아 있던
갭 4개를 메웠다. 그 글의 실패 요인 중 "프롬프트만으로 복잡도 판정 불가"·"캐시가
라우팅보다 낫다"·"모델이 튀면 일관성이 깨진다"는 이 도구가 구조적으로 이미 회피하고
있다 — 사후 에피소드 채점이고, 위임은 메인 캐시 프리픽스를 건드리지 않는 별도
컨텍스트이며, 메인 모델은 고정이기 때문. 남은 것은 아래 넷.

**① rule-health v2 — 프록시에서 실측으로.** 기존 에러율의 분모는 "비싼 모델이 직접
처리했는데 형태상 위임 가능해 보이던 에피소드"였다. 즉 룰이 **실제로 발동했을 때의
성패는 한 번도 재지 않았다** — 룰이 매번 실패해도 신호가 안 움직인다. Claude Code는
서브에이전트 실행을 `<세션>/subagents/agent-*.jsonl`에 따로 남기고
`.meta.json`의 `toolUseId`가 부모 transcript의 Task 호출과 정확히 조인되므로, 실제
위임 결과를 측정할 수 있다. 실측 위임이 5건 이상 쌓이면 그 값이 프록시를 대체한다
(에피소드 10건보다 낮은 문턱 — 실측은 룰 발동의 직접 증거라 적은 표본으로도 유효).
저자 로그 14일 기준 106세션 중 4세션·18런, `toolUseId` 조인 성공률 100%.

**② 상대 티어.** 기존 게이트는 "haiku인가?" 하나뿐이라 Sonnet 세션에서도 T1
(sonnet 위임) 후보가 생겼다 — 컨텍스트만 새로 쌓고 단가 차이는 0인 순손해. 가격
랭크(haiku 0 · sonnet 1 · opus 2 · fable 3)를 도입해 **목표 티어가 실제로 더 싼
경우에만** 후보를 만든다. rule-health 분모에도 같은 게이트를 적용해야 분자·분모가
어긋나지 않는다.

**③ 룰별 절감액.** 룰의 가치는 절감량인데 레지스트리엔 반복 횟수와 에러율뿐이었다.
위임 실행의 토큰을 세션 모델 단가로 되돌려 계산한 차액을 14일 윈도 스냅샷으로
누적한다(토큰량 동일 가정이라 근사 — 표기도 `~$`). 실측 위임이 없는 룰은 `$0`이
아니라 `—`로 표시한다: 둘은 정반대를 뜻한다.

**④ probe-then-commit 예산.** 룰은 통계로 만들어지지만 **발동은 요청 텍스트만 보고**
일어난다 — 그리고 난이도는 대개 첫 툴콜 뒤에 드러난다(HN 댓글: "Most of what makes a
task hard shows up after the first tool call"). 이 불일치는 원리적으로 못 없애므로,
대신 오판 비용에 상한을 건다: 룰 문구에 캘리브레이션된 상한(T2는 호출 8회·출력 p25,
T1은 출력 p75)을 명시하고 초과·에러 시 서브에이전트가 멈춰 진행분만 보고하고 메인이
이어받게 한다. 문구는 저장된 룰 텍스트에 굽지 않고 렌더 시점에 조립하므로
(`composeRuleText`) 예산 도입 이전에 승격된 룰도 함께 적용받고, promote 프리뷰와
파일 내용이 어긋날 수 없다.

범위 제외 — **오프라인 bakeoff**(과거 T2 에피소드를 haiku로 리플레이해 승격 전 검증):
LLM 호출이 발생해 "전 과정 로컬·LLM 0회" 원칙과 충돌하므로 별도 옵트인으로 미룬다.

### 기존 라우터들의 접근과 수치
- **RouteLLM** (lmsys): 쿼리 텍스트만 보고 "강한 모델이 이길 확률"을 예측하는 이진
  분류기. Chatbot Arena 선호 데이터 8만 건으로 학습. MT Bench에서 강모델 호출 13.4%로
  품질 95% 유지, 비용 최대 3.66x 절감. **실행 로그(도구 호출·토큰)는 안 씀** —
  텍스트 기반 학습 분류기 계열. [arxiv 2406.18665, 3-0 확정]
- **FrugalGPT**: 싼 모델부터 시도하고 응답 신뢰도 스코어러가 낮게 보면 위로 올리는
  캐스케이드. GPT-4 대비 최대 98% 비용 절감 or 동비용 +4% 정확도. "실패하면 승급"
  구조의 원형. [arxiv 2305.05176, 3-0]
- **RouterArena** (2025): 학술·상용 라우터 전부 오라클(90.9%)에 크게 못 미침(1위 66.9).
  결정적 발견 두 가지: ① 기존 라우터는 **비싼 모델로 과잉 라우팅**하는 체계적 편향이
  있고 "싼 모델로 충분한 경우를 인식하는 것"이 미개척 방향, ② 난이도를 텍스트가 아니라
  **"42개 모델 중 몇 개가 실제로 맞혔나"라는 결과(outcome) 로그로 정의** — 로그 기반
  오프라인 난이도 라벨링의 학술적 근거. [arxiv 2510.00202, 3-0]
- **Routing collapse**: 학습형 라우터는 예산이 커지면 최강 모델만 고르는 퇴화로 수렴.
  같은 벤치마크에서 오라클은 최강 모델이 **20% 미만의 쿼리에만 필요**. [arxiv 2602.03478, 3-0]
- **휴리스틱 신호의 실전 사용**: 입력 길이, 명령형 키워드(analyze/compare/evaluate),
  어휘 희귀도, 구문 복잡도 — LLM 호출 없이 계산 가능한 신호들이 프로덕션 라우팅에
  실제로 쓰임. [arxiv 2603.04445 서베이, 2-1]
- **응답 레벨 신호**: 신뢰도·토큰 확률·검증기 출력 등 "생성 후" 신호는 쿼리 특징과
  구분되는 별도 신호 클래스로 인정됨 → 로그의 실패/재시도 흔적은 정당한 라우팅 신호.
  [같은 서베이, 3-0]

### Claude Code 특유의 검증된 사실
- 서브에이전트 `model:` frontmatter(haiku/sonnet/opus/fable/inherit)는 **비용 통제용
  1급 메커니즘**이고 Anthropic이 공식적으로 "Haiku 등 싼 모델로 라우팅해 비용 통제"를
  권장. [code.claude.com/docs/sub-agents, 3-0 ×2]
- Claude Code 본체는 **자동 모델 라우팅을 전혀 하지 않음** — 사소한 턴도 세션 모델이
  전체 컨텍스트를 재전송하며 처리. (= 이 도구가 메우는 공백)
- 세션 JSONL에서 Read:Edit 비율, 선행 Read 없는 Edit, 반복 Edit, 자기수정 루프 등
  **행동 메트릭을 LLM 없이 오프라인 계산 가능**하다는 선행 사례 존재
  (claude-session-analyzer: Read:Edit >6 양호 / <2 저하 등 구체 임계값 공개).
- 실무자 티어링 사례: 오케스트레이터(상위 모델) + 실행(haiku급) 분리로 토큰 5–10x 절감
  주장(mindstudio); plan mode·아키텍처 논의 → 최상위, 첫 Edit/Write/Bash → 중간,
  질문·탐색 → 최하위라는 트리거 설계(GitHub issue #67898).

### 설계에 주는 함의
1. **"쉬운 것만 확실히 내리는" 보수적 강등 전략이 정확히 미개척 지대다** — 기존
   라우터의 실패는 전부 과잉 승급 쪽이고, 오라클 기준 최상위 모델이 필요한 쿼리는
   20% 미만이다. 저자 로그에선 73%가 최상위 티어에 남아 있으므로 헤드룸이 크다.
2. **난이도 라벨은 텍스트 추정이 아니라 결과(outcome)에서 얻어라** — RouterArena
   방식. 우리 로그에는 이미 결과가 있다: 도구 에러, 재시도, 에피소드 길이.
3. **임계값은 절대 상수가 아니라 사용자 자신의 분포에서 보정하라** — RouteLLM의
   공식 한계가 "고정 임계값은 쿼리 분포가 바뀌면 어긋난다"이다.
4. **실패 시 승급(escalation) 경로가 있으면 강등 오판 비용이 작아진다** — FrugalGPT
   캐스케이드의 교훈. Claude Code에선 서브에이전트가 실패를 보고하면 메인 모델이
   이어받는 형태로 자연 구현된다.
