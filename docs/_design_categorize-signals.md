# 설계 검토: 프롬프트 regex 분류는 너무 얕은가?

계기: 사용자 질문 — "단순히 프롬프트 문자열 regex만으로 판단해도 되는가" (2026-07-14)

## 결론 먼저

**얕은 게 맞고, 더 깊은 신호가 이미 공짜로 있다.** 다만 "regex가 어디에 쓰이는지"를
구분해야 한다 — 티어 판정(T0/T1/T2)은 이미 행동 기반(호출 수·출력 토큰·mutating·에러)이고,
regex는 **카테고리 라벨링**(어느 에이전트로 위임할지 + 예시 문구)에만 쓰인다.
그래서 얕음의 피해 범위는 "잘못된 위임 대상 추천 + 오염된 예시/통계"로 한정되지만,
그게 바로 사용자가 두 번 연속 체감한 문제이기도 하다.

## 신호별 깊이 비교

| 신호 | 깊이 | 비용 | 현재 상태 |
|---|---|---|---|
| 프롬프트 키워드 regex | 얕음 — 표현에 의존, 동의어·우회 표현에 취약 | 0 | 사용 중 (categorize) |
| 에피소드 행동 지표 (calls/out/mutating/errors) | 중간 — 결과 기반 | 0 | 사용 중 (tierOf) |
| **도구 사용 히스토그램** (어떤 툴을 몇 번 썼나) | **깊음 — 말이 아니라 실제로 한 일** | **0 (이미 파싱 중, 집계만 안 함)** | 미사용 ← 핵심 기회 |
| LLM 배치 분류 (haiku) | 깊음 | 토큰 소모 — "zero token cost" 설계 원칙 위배 | 부적합(상시), promote 시 검증용으론 가능 |
| 임베딩 유사도 | 깊음 | 로컬 모델 의존성 — CLI에 과함 | 부적합 |

## 제안: 행동 우선(behavior-first) 분류

에피소드가 **실제로 실행한 도구 구성**이 카테고리의 ground truth다:

- Bash 위주 + Edit/Write 없음 → `run` (명령 실행)
- Read/Grep/Glob 위주 → `explore`/`read`
- Write 위주 + 낮은 Read → `translate`류 (정형 생성)
- 도구 거의 없음 + 출력만 → `read` (설명/요약)

구현 경로: `session-records.js:84-86`이 이미 `b.name`을 읽으므로, 레코드에
`toolCounts: {Bash: n, Read: n, ...}` 한 필드만 추가하면 됨. 파싱 비용 증가 없음.

### 판정 순서 (제안)

1. **게이트 선처리** (점수 경쟁 밖): paste(길이), ESCALATE(비가역·설계 키워드) — 성격이 다른 컷오프
2. **도구 히스토그램으로 1차 분류** — 에피소드가 한 일 기반. 신뢰도 높음
3. **키워드 스코어링은 tie-break·보조** — 도구 신호가 애매할 때(도구 0~1회 사용 등)만
   가중 키워드 점수(강한 신호 2점·범용어 1점, 동점 시 기존 순서)로 결정
4. (선택) promote 시점에만 haiku로 예시 8건 재검증 — 후보당 수백 토큰, 상시 스캔은 여전히 0토큰

### 왜 이 순서인가

- "테스트 통과했는지 확인해줘"라고 말했어도 실제로 `npx playwright test`를 돌렸다면
  그 에피소드는 run이다 — 표현이 아니라 행동이 진실. 키워드 순서·가중치 논쟁이
  대부분 무의미해짐 (지난 두 차례의 수정이 모두 표현 층위의 땜질이었음)
- 반대로 도구를 안 쓴 순수 문답 에피소드는 키워드 말고 판단 근거가 없으므로
  스코어링 폴백이 여전히 필요
- 실시간 위임 판단은 어차피 ratchet-model.md를 읽는 LLM(깊은 판단자)이 하므로,
  이 분류기는 "룰 후보 제안의 정확도"만 책임지면 됨 — 배치·오프라인·0토큰 제약 유지

## 한계 (솔직하게)

- 도구 히스토그램도 오염 가능: 메인 모델이 과잉 행동한 에피소드(간단한 질문에 grep 10번)는
  실제 난이도보다 무겁게 분류됨. 단, 이건 "그 요청이 실제로 유발한 비용" 관점에서는
  오히려 올바른 신호이기도 함
- 카테고리 6종 자체가 거친 분류. 정밀도가 더 필요해지면 그때 LLM 검증 단계(4번)를 켜는
  것이 임베딩 도입보다 싸고 단순함

## 구현 완료 (2026-07-14, v3.4.0)

- `src/session-records.js` — 레코드에 `toolCounts` 히스토그램 추가 (같은 requestId 누적 병합)
- `src/route-scan.js` — 판정 순서: paste 게이트 → `behaviorPool(toolCounts)`로 후보군 축소
  (Bash 우세→run, Read/Grep 우세→lookup군, 호출 2회 미만·혼합은 판단 보류) →
  가중 키워드 스코어링(강한 신호 2점·범용어 1점, 동점 시 CATEGORIES 순서)으로 최종 선택.
  행동 신호만 있고 키워드가 없으면 pool 대표값, 둘 다 없으면 null.
- 검증: 19케이스 ALL PASS — 기존 9케이스 회귀 없음 + 스코어링(다수 키워드 승리) +
  행동 신호(모호한 프롬프트를 도구 사용이 결정) + 게이트 케이스
- 재스캔 결과: easy 에피소드 65→111건(15%→26%) — 키워드 regex가 못 잡던
  에피소드를 행동 신호가 분류하게 된 효과
